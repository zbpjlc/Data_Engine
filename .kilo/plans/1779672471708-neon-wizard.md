# PaddleOCR V1.6 vs GLM OCR vs 自研模型 三模型对比方案

## 1. 背景

当前 Data Engine 已完成 M1-M4 的基础架构，pipeline 为：

```
ingest → embed → cluster → [scored → inferred → compared → bucketed] 
                                    ↑
                               CMCV 阶段（待实现）
```

`UnifiedSampleRecord` 中已预留 `block_list`、`text_spans`、`table_structure`、`formula_spans` 等结构化字段（`models.py:109-113`），`manifests.py` 中以 JSON string 存储（`manifests.py:34-38`）。

现在需要接入三个 OCR 模型：
1. **PaddleOCR V1.6** — 远程服务
2. **GLM OCR** — 远程服务
3. **自研模型** — 远程服务

三者都依赖 pp-layout 做版面分析（本地安装）。目标是：**在 element-sample 阶段跑三模型推理，在 CMCV 阶段做一致性比较，最终写入难度分桶。**

## 2. 架构设计

### 2.1 核心原则：本地 Layout + 远程 OCR 服务

```
        本地 (Data Engine 服务器)                    远程服务
  ┌─────────────────────────────┐            ┌──────────────────┐
  │      pp-layout              │            │  PaddleOCR V1.6  │
  │  (PicoDetection, 本地安装)   │ ─ bbox →  │  HTTP API 服务    │
  │  CPU 推理即可                │            └────────┬─────────┘
  │                             │                     │
  │                             │            ┌────────┴─────────┐
  │                             │            │    GLM OCR        │
  │                             │ ─ bbox →   │  HTTP API 服务    │
  │                             │            └────────┬─────────┘
  │                             │                     │
  │                             │            ┌────────┴─────────┐
  │                             │            │    自研模型        │
  │                             │ ─ bbox →   │  HTTP API 服务    │
  │                             │            └────────┬─────────┘
  └─────────────────────────────┘                     │
                   ↑                                  │
                   │          三模型结果汇合            │
                   └──────────────┬───────────────────┘
                                  │
                           element.lance
                                  │
                            ┌─────┴─────┐
                            │   CMCV    │  ← 一致性比较（本地）
                            └─────┬─────┘
                                  │
                         easy / medium / hard
```

### 2.2 部署模型

| 组件 | 部署方式 | 原因 |
|------|---------|------|
| pp-layout | **本地安装** | 轻量检测模型，CPU 推理即可；三个 OCR 服务的前置依赖 |
| PaddleOCR V1.6 | **远程服务** | HTTP API 调用 |
| GLM OCR | **远程服务** | HTTP API 调用 |
| 自研模型 | **远程服务** | HTTP API 调用 |
| CMCV 比较引擎 | **本地运行** | 纯字符串/结构比较，不需要模型 |

### 2.3 为什么 pp-layout 本地而不是服务？

1. **pp-layout 是轻量检测模型**（PicoDetection），本地 CPU 推理毫秒级
2. **它是三个 OCR 服务的前置依赖**：如果 pp-layout 也是服务，每次处理一张图要先调 layout 服务拿 bbox，再把 bbox 发给三个 OCR 服务，链路多一跳
3. **bbox 一致性保障**：本地跑一次 layout，得到确定的 blocks，直接传给三个远程 OCR 服务，保证输入完全一致
4. **离线可用**：不依赖额外的 layout 服务上线

### 3.2 `ocr/base.py` — 抽象基类

```python
from abc import ABC, abstractmethod
from pathlib import Path
from dataclasses import dataclass

@dataclass
class LayoutBlock:
    """pp-layout 检测到的版面块"""
    block_type: str        # "text" | "table" | "formula" | "figure" | "title"
    bbox: list[float]      # [x1, y1, x2, y2]
    confidence: float

@dataclass
class OCRResult:
    """单个 region 的 OCR 结果（来自远程服务响应）"""
    block_type: str
    bbox: list[float]
    text_content: str
    confidence: float
    raw_output: dict       # 服务原始响应，用于 debug

class BaseOCREngine(ABC):
    """OCR 引擎抽象基类（所有引擎都是远程服务客户端）"""
    
    @property
    @abstractmethod
    def model_name(self) -> str: ...
    
    @property
    @abstractmethod
    def model_role(self) -> str:  # "target" | "judge"
        ...
    
    @abstractmethod
    def recognize_regions(
        self, 
        image_path: Path, 
        regions: list[LayoutBlock]
    ) -> list[OCRResult]:
        """将图片 + bbox 发送给远程 OCR 服务，返回识别结果"""
        ...
```

关键设计：
- **所有 OCR 引擎接收相同的 `LayoutBlock` 列表**，保证 bbox 对齐
- **所有引擎都是远程服务客户端**，通过 HTTP API 调用
- **pp-layout 是唯一本地组件**，负责生成 `LayoutBlock`

### 3.7 `ocr/cmcv.py` — 一致性比较引擎

```python
class CMCVEngine:
    """
    Cross-Model Consistency Verification（三模型）
    
    从 element.lance 读取同一行的三个模型结果，逐 block 比较一致性
    """
    
    def compare_page(self, blocks: list[dict]) -> dict:
        """
        输入: 一个页面的所有 block（来自 element.lance 的查询结果）
              每个 block 包含 paddle_text/glm_text/self_text 等三列
        
        流程:
        1. 遍历每个 block，按 block_type 分流比较
        2. 对每个 block，计算三对比较:
           - paddle vs glm
           - paddle vs self
           - glm vs self
        3. 判断每个 block 的一致性模式
        4. 汇总所有 block → 页面级分桶
        
        返回:
        {
            "block_count": 12,
            "all_agree_count": 9,       # 三个模型一致的 block 数
            "partial_agree_count": 2,   # GLM+Paddle一致、自研不一致的 block 数
            "all_disagree_count": 1,    # 三个都不一样的 block 数
            "tier": "medium",           # 页面级分桶：取最差 block
            "details": [
                {"block_idx": 0, "type": "text",    "pattern": "all_agree"},
                {"block_idx": 1, "type": "table",   "pattern": "partial_agree"},
                {"block_idx": 2, "type": "formula",  "pattern": "all_disagree"},
                ...
            ]
        }
        """
        ...
    
    def _compare_block(self, block: dict) -> str:
        """
        对单个 block 判断一致性模式
        
        返回: "all_agree" | "partial_agree" | "all_disagree"
        
        规则:
        - 先按 block_type 选择比较算法（levenshtein / teds / cdm）
        - 计算三对相似度: sim_pg (paddle-glm), sim_ps (paddle-self), sim_gs (glm-self)
        - 定义 threshold = 0.9（可配置）
        
        all_agree:     sim_pg >= threshold AND sim_ps >= threshold AND sim_gs >= threshold
        partial_agree: sim_pg >= threshold AND (sim_ps < threshold OR sim_gs < threshold)
                       即 GLM 和 Paddle 一致，但自研不一致
        all_disagree:  sim_pg < threshold
                       即 GLM 和 Paddle 本身就不一致
        """
        ...
    
    def _compare_text(self, text_a: str, text_b: str) -> float:
        """文本相似度：归一化编辑距离（Levenshtein）"""
        ...
    
    def _compare_table(self, table_a: dict, table_b: dict) -> float:
        """表格相似度：TEDS（Tree-Edit-Distance-based Similarity）"""
        ...
    
    def _compare_formula(self, formula_a: str, formula_b: str) -> float:
        """公式相似度：CDM（Character Detection Matching）"""
        ...
    
    def _assign_tier(self, block_patterns: list[str]) -> str:
        """
        页面级分桶（不加权，取最差 block）：
        
        如果任一 block 是 all_disagree → 页面 hard
        如果任一 block 是 partial_agree（无 all_disagree）→ 页面 medium
        如果所有 block 都是 all_agree → 页面 easy
        """
        ...
```

关键变化：**比较的输入是 element.lance 中同一页面的所有 block 行**，而不是两个独立 manifest 的 join 结果。每个 block 的 `paddle_text` 和 `glm_text` 直接在同一行读取。

## 4. 集成到现有 Pipeline

### 4.1 Stage 流转

```
ingested → embedded → clustered → scored → inferred → compared → bucketed
                                                    ↑
                                              CMCV 阶段
```

新增两个 stage 的处理逻辑：

1. **`element-sample`（inferred 阶段）**：
   - 本地调用 pp-layout 做版面分析 → 得到 blocks (type + bbox)
   - 将图片 base64 + bbox 列表分别发送给三个远程 OCR 服务
   - **三个服务的结果写入同一张 `element.lance`，每个 block 一行，`paddle_*`/`glm_*`/`self_*` 并列**
   - 同时将 PaddleOCR 的标准化输出写回 `ingest.lance` 的 `block_list` / `text_spans` 等字段（作为默认视图）
   - 状态推进: `clustered → inferred`

2. **`cmcv`（compared 阶段）**：
   - 从 `element.lance` 读取每个页面的所有 block 行
   - 逐 block 计算三对比较（paddle-glm, paddle-self, glm-self），判断一致性模式
   - 将 `consistency_pattern` 和 `block_diff_json` 写回 `element.lance` 对应行
   - 通过 `GROUP BY sample_id` 聚合：取最差 block 的一致性模式作为页面级 tier
   - 将 tier 写回 `ingest.lance` 的 `difficulty` 字段
   - 状态推进: `inferred → compared → bucketed`

### 4.2 数据存储设计：单表合一

```
manifests/
├── ingest.lance    # 页面级基础数据 + embedding + difficulty
└── element.lance   # 逐 block：三模型 OCR 结果 + 一致性比较结果
```

**不需要 `cmcv.lance`。** CMCV 结果直接写回 `element.lance`：
- block 级比较结果写入 `consistency_pattern` 和 `block_diff_json` 列
- 页面级 tier 通过 `GROUP BY sample_id` 聚合实时计算，写回 `ingest.lance` 的 `difficulty` 字段
- 少维护一个文件，所有 block 级数据在同一张表

**核心变更：三个模型的 OCR 结果写入同一张 `element.lance`，按 block 行对齐。**

原因：
1. 三个模型处理的是完全相同的 block（来自同一次 pp-layout），天然按行一一对应
2. 比较时直接同行读取三个模型的输出，不需要 join `sample_id + block_idx`
3. Web Console 展示对比时，一条查询就能拿到三列结果
4. 如果需要重跑单个模型，可以用 `merge_insert` 按 `sample_id + block_idx` 只更新对应模型的列

#### 行粒度：一个 block 一行

每行代表一个 page 中的一个 layout block，三个模型的识别结果作为并列字段存储：

```
┌──────────┬───────────┬────────────┬─────────────────┬─────────────────┬─────────────────┐
│ sample_id│ block_idx │ block_type │ paddle_text     │ glm_text        │ self_text       │
├──────────┼───────────┼────────────┼─────────────────┼─────────────────┼─────────────────┤
│ page_001 │ 0         │ text       │ "第一章 绪论..." │ "第一章 绪论..." │ "第一章 绪论..." │ ← all_agree
│ page_001 │ 1         │ table      │ paddle_table... │ glm_table...    │ self_table...   │
│ page_001 │ 2         │ formula    │ "E=mc^2"        │ "E = mc^{2}"    │ "E=mc²"         │ ← partial_agree
│ page_002 │ 0         │ text       │ "..."           │ "..."           │ "..."           │
└──────────┴───────────┴────────────┴─────────────────┴─────────────────┴─────────────────┘
```

好处：
- 同一行里两个模型的结果直接相邻，比较时零成本
- 每个 block 有独立的 `block_idx`，支持按 block 粒度人工复核
- block 类型字段天然支持按 text/table/formula 分组统计

字段命名规则：`{model}_{field}`，如 `paddle_text`、`glm_text`、`self_text`。

- `consistency_pattern`：block 级一致性模式（all_agree / partial_agree / all_disagree）

### 4.4 UnifiedSampleRecord 更新

不需要修改 `UnifiedSampleRecord` 本身的 schema，因为：
- `block_list` / `text_spans` / `table_structure` / `formula_spans` 字段已经存在
- 在 `inferred` 阶段，将 Target Model (PaddleOCR) 的标准化输出写回 `ingest.lance` 的对应字段（作为默认视图）
- 两个模型的逐 block 详细结果存在 `element.lance` 中
- `difficulty` 字段在 `bucketed` 阶段由 CMCV 写入

```python
class ElementBlockRecord(BaseModel):

    paddle_raw: dict | None = None

    # GLM OCR 结果
    glm_text: str | None = None
    glm_confidence: float | None = None
    glm_table: dict | None = None
    glm_formula: str | None = None
    glm_raw: dict | None = None

    # 自研模型结果
    self_text: str | None = None
    self_confidence: float | None = None
    self_table: dict | None = None
    self_formula: str | None = None
    self_raw: dict | None = None

    # Block 级比较（CMCV 阶段写入 element.lance）
```

- 不需要单独的 cmcv.lance

```bash
    --layout-provider pp_layout

# 2. 一致性比较（compared → bucketed 阶段）
#    从 element.lance 读取三模型结果 → 逐 block 比较 → 写回 element.lance + 更新 ingest.lance 的 difficulty
data_engine cmcv --source-id <id> --batch <batch_id>

# 3. 单独重跑某个模型（不影响其他两个）
#    只更新 element.lance 中对应模型的列（通过 merge_insert）
data_engine element-sample --source-id <id> --batch <batch_id> \
    --models self_ocr \
    --resume
```

## 8. 关键注意事项

### 8.1 服务调用容错

- PaddleOCR 和 GLM OCR 都是远程服务，需要处理：
  - **超时重试**：单个 block 请求超时后重试（建议 3 次）
  - **服务不可用**：某个服务宕机时，跳过该模型，只跑另一个，后续用 `--resume` 补跑
  - **部分失败**：某个 block 识别失败时，标记为 null，不影响其他 block
  - **并发控制**：控制同时发给服务的请求数，避免打爆服务端

### 8.2 pp-layout 输出格式兼容

PaddleDetection 的 PP-Structure 输出格式为：
```python
[{
    "type": "text",
    "bbox": [x1, y1, x2, y2],
    "res": ...  # OCR 结果
}]
```

需要转换为 `LayoutBlock` 统一格式，PaddleOCR 和 GLM OCR 都基于这个格式工作。

### 8.3 断点续跑（基于 merge_insert）

- `element.lance` 中每个 block 行有 `sample_id + block_idx` 联合主键
- 重跑 PaddleOCR 时，只 `merge_insert` 更新 `paddle_*` 列，不碰 `glm_*` / `self_*` 列
- 重跑 GLM OCR 时，只更新 `glm_*` 列，不碰 `paddle_*` / `self_*` 列
- 重跑自研模型时，只更新 `self_*` 列，不碰 `paddle_*` / `glm_*` 列
- 重跑 CMCV 时，读取 `element.lance` → 计算 → `merge_insert` 更新 `consistency_pattern` / `block_diff_json` 列
- 已完成的模型结果不会被覆盖（`merge_insert` 只更新指定列）

```python
# 重跑 PaddleOCR 的示例逻辑：
# 1. 读取 element.lance 中 paddle_text IS NULL 的行
# 2. 对这些行调用 PaddleOCR 服务
# 3. merge_insert 按 sample_id + block_idx 更新 paddle_* 列
ds.merge_insert(["sample_id", "block_idx"]).when_matched_update_all().execute(paddle_table)

# 重跑 CMCV 的示例逻辑：
# 1. 读取 element.lance 中 consistency_pattern IS NULL 的行
# 2. 对这些行计算三对比较
# 3. merge_insert 更新 consistency_pattern / block_diff_json 列
# 4. 聚合得出页面级 tier，更新 ingest.lance 的 difficulty
```

### 8.4 扩展性（新模型接入）

- 后续接入第三个模型（如 Qwen-VL OCR），只需：
  1. 新增一个 `BaseOCREngine` 子类（远程服务客户端）
  2. 给 `element.lance` 加一组 `{new_model}_xxx` 列（`ALTER` 或重建 schema）
  3. 用 `merge_insert` 填充新列，已有的 `paddle_*` / `glm_*` 列不受影响
- CMCV 的 `backend_triplet` 字段记录了比较使用的模型组合
- 标准化层保证所有模型输出可以互相比对
- `element.lance` 的列式存储天然支持"只读取需要的模型列"，不会因为模型增多而 I/O 膨胀
- 新增模型只需在 `config.yaml` 的 `ocr.engines` 下加一个服务地址配置
