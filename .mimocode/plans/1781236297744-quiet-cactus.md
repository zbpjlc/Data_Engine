# Embedding 独立服务方案

## 问题背景

web_app 主进程初始化 CUDA 后，后台线程 spawn 子进程调用 ViT 推理会因 cuBLAS LT 线程安全问题崩溃（`Invalid handle. Cannot load symbol cublasLtCreate`, rc=-6）。经过大量测试（subprocess.run、multiprocessing.spawn、常驻 worker），在 web_app 运行环境下均无法稳定工作。

## 方案：Embedding 独立 HTTP 服务

参考现有 OCR 服务模式（paddle_ocr/glm_ocr/self_ocr 均为独立 HTTP 服务），将 embedding 提取也做成独立 HTTP 服务。

### 架构

```
web_app (GPU 0, CUDA 已初始化)
    ↓ HTTP POST /embed  (batch_size=32)
embedding_server (独立进程, GPU 1, 独立 CUDA 上下文)
    ↓ 加载 SigLIP2 → 推理 → 返回 embeddings
```

### 新建文件

**`data_engine/ocr/embedding_server.py`** — 独立 embedding HTTP 服务

```python
# FastAPI 服务，启动时加载 SigLIP2，监听 8090 端口
# POST /embed  body: {"images": [base64_encoded_bytes...], "batch_size": 32}
# 返回: {"embeddings": [[float...], ...]}
# GET /health  → {"status": "ready", "gpu": "cuda:1"}
```

- 独立进程，独立 CUDA 上下文，不受 web_app 影响
- 模型只加载一次，常驻内存
- 支持 batch_size 可配置（默认 32）
- 通过 `config.yaml` 配置端口和 GPU

### 修改文件

**`data_engine/config.yaml`** — 新增 embedding 服务配置
```yaml
embedding:
  server:
    host: "127.0.0.1"
    port: 8090
    gpu_id: 1
    batch_size: 32
```

**`data_engine/ocr/layout_features.py`** — 改用 HTTP 调用
```python
# 替换 local_extractor.extract_embeddings_from_bytes_batch()
# 改为:
import requests
resp = requests.post("http://127.0.0.1:8090/embed", json={"images": img_b64_list, "batch_size": 32})
results = resp.json()["embeddings"]
```

**`data_engine/web_app.py`** — 启动时检查/启动 embedding 服务
```python
# 在 web_app 启动前检查 embedding_server 是否运行
# 如果没有，spawn 一个独立进程启动它
```

**`data_engine/embedding.py`** — 保留 CLIPEmbeddingExtractor 类（供 embedding_server 使用），新增 `extract_embeddings_via_http()` 函数

### 优势

| 对比 | subprocess 方案 | 独立 HTTP 服务 |
|------|----------------|---------------|
| CUDA 隔离 | fork 可能继承父进程状态 | 完全独立进程 |
| 模型加载 | 每次 spawn 重新加载 (~3s) | 启动时加载一次 |
| batch_size | 受限于进程间通信 | 自由设置 32+ |
| 错误恢复 | 进程崩溃需重新 spawn | 服务可自动重启 |
| 复用性 | 仅内部调用 | 可被其他工具调用 |

### 验证

1. 单独启动 embedding_server，用 curl 测试 `/embed` 端点
2. 启动 web_app，触发 Element-Type 聚类
3. 确认 table embedding 生成成功（不再 rc=-6）
4. 确认 batch_size=32 正常工作，吞吐量提升 10-30x

# 三种聚类/索引方案对比 + 前端可视化 + 建议

## 一、三种方案概览

| 维度 | 向量索引 (IVF_PQ) | Page-Level Clusters | Element-Level Clusters |
|------|-------------------|--------------------|-----------------------|
| **聚类对象** | ingest.lance 全量样本的 768d embedding | ingest.lance 全量样本的 768d embedding | text/formula/table.lance 中每个 block 的 768d embedding |
| **算法** | Lance IVF_PQ (倒排索引 + 乘积量化) | MiniBatchKMeans (sklearn) | MiniBatchKMeans (sklearn), 按 block_type 独立聚类 |
| **粒度** | 页级（每张原图 = 1 条） | 页级（每张原图 = 1 条） | Block 级（每页可能有 N 个 block） |
| **自动选 K** | 固定分区数（用户指定，默认 256） | 轮廓系数自动选 K (2~10) | 轮廓系数自动选 K (2~10)，text/formula/table 各自独立 |
| **输出** | IVF_PQ 索引 + 桶分布统计 | cluster_id 写回 ingest.lance | element_clusters.json（簇统计 + labels） |
| **用途** | 近似最近邻搜索（ANN），检索相似文档 | 页面级质量控制、按簇抽样 | Block 级质量控制、细粒度按簇抽样 |
| **已有前端** | ✅ 完善：进度条 + 桶分布图 + 分区详情 | ⚠️ 基础：在 Page_CMCV tab 下 | ⚠️ 基础：Element-Level 卡片，列表展示 |

## 二、现状分析

### 1. 向量索引 (IVF_PQ)
- **文件**: `data_engine/index.py`
- **API**: `POST /api/index/{source_id}`, `GET /api/index/{source_id}/{batch_id}/stats`
- **前端**: `panel-index` — 桶分布柱状图 (Chart.js)、分区/向量/平均桶大小统计卡片、点击分区查看样本
- **参数**: num_partitions=64, num_sub_vectors=16 (config.yaml)
- **数据**: 金融数据 2,494,825 条 embedding，64 分区

### 2. Page-Level Clusters
- **文件**: `data_engine/clustering.py` (`cluster_records` 函数)
- **API**: `POST /api/cluster/{source_id}`
- **前端**: 在 `panel-bucket` (Page_CMCV tab) 下，聚类后按簇抽样
- **工作流**: 对 ingest.lance 全部样本的 embedding 做 KMeans → 写回 cluster_id → 按簇抽样 → 送 OCR/Layout

### 3. Element-Level Clusters
- **文件**: `data_engine/ocr/layout_features.py` (`cluster_by_type`, `cluster_all_types`)
- **API**: `POST /api/element-clusters/{source_id}/{batch_id}`, `GET ...`
- **前端**: `Element-Level` 卡片 — text/formula/table 三列展示簇统计
- **数据**: 金融数据 text=571,422 blocks, table=75,370 blocks, formula=0
- **输出**: `element_clusters.json` 含 n_clusters, silhouette, clusters (size + bbox_mean), labels

## 四、建议

### 推荐工作流
```
ingest.lance → embedding → 向量索引 (ANN 检索)
                ↓
         pp-layout → text/formula/table.lance
                ↓
         Element-Level 聚类 → 按簇抽样 → OCR 修复/验证
                ↓
         Page-Level 聚类 → 按簇抽样 → 全局质量评估
```

### 各方案适用场景
1. **向量索引**: 适合相似文档检索、去重、异常检测（空桶/大桶可识别分布不均）
2. **Page-Level**: 适合全局质量评估、按难度分层抽样、OCR 结果验证
3. **Element-Level**: 适合细粒度质量控制、按 block 类型分析、精准抽样验证 OCR/LaTeX/表格识别

### 关键发现
- Element-Level 的 **table 簇为 0** — 需要修复 embedding 生成（已在进行 spawn subprocess 修复）
- formula.lance **损坏** — 两个数据集都需要重建
- 向量索引用 64 分区 vs 配置默认 256 — 当前 64 分区对 2.4M 数据偏少，建议增至 128~256
- Page-Level 聚类和 Element-Level 聚类使用相同的 KMeans 算法，但粒度不同，互补使用效果最佳
